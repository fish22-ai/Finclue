## 决策一：抓取层不自研浏览器，但复用现成的 socai

- 状态：**2026-09-13 修订**（原为「不引入浏览器」，现改为「不自研，但复用 socai」）

### 背景
候选源中多个被 Cloudflare 拦截（一亩三分地、WSO）。常见解法是上 Playwright/Selenium 模拟真实浏览器。
另外小红书裸 HTTP 是 302 登录墙，但**用户本机已装 `socai`**，可用本人账号完整抓取。

### 决策
**不自研浏览器自动化，但将 `socai` 作为小红书源的适配器接入。**

具体：
1. 小红书**一律经 `socai xhs`**，不自己写 Playwright/Selenium
2. 其他源仍只用 `requests` + `feedparser` + `lxml/bs4`
3. **不为任何 Cloudflare 拦截源引入浏览器方案**（一亩三分地、WSO 直接放弃）

### 理由
- socai 已经是**成熟、已登录、已验证可用**的专用工具，自研是重复造轮子
- 自研浏览器自动化去打 Cloudflare 属于典型的反爬绕过，且投入产出比低
- socai 走的是**本人账号正常访问**，性质不同于破解反爬

### 后果
- 小红书 `actual_bar` / `return_offer` / `wlb` / `interview_content` 字段有了来源
- 引入了对外部闭源二进制的依赖：socai 停止维护 / 免费版限流 → 该源受影响
- 需要人工介入：**登录态失效时需用户重新扫码**（`reason: "login_required"`）

## 决策二：AI 上游沿用 agentrouter 中转（有条件）

### 背景
用户已通过 CC Switch 配置了 `agentrouter.org` → `deepseek-v4-flash`，
凭据在 `~/.cc-switch/cc-switch.db`。实测该端点**可被脚本调用**，
但**必须伪造 Claude Code 客户端指纹头**（`user-agent: claude-cli/...` 等）。

### 决策
**MVP 阶段沿用，但必须做到：**
1. 凭据**从 cc-switch.db 运行时读取**或走环境变量，**不落盘到项目仓库**
2. 失败时优雅降级（重试 1 次 → 记日志 → 跳过该条），不能让整条 pipeline 崩
3. 记录每次调用成本，便于评估

### 风险（必须知晓）

| 风险 | 说明 |
|---|---|
| **非官方服务** | `agentrouter.org` 是第三方中转，非 Anthropic 官方。服务条款、数据处理方式均不透明 |
| **稳定性** | 实测中出现过 `unauthorized client detected` 与上游 401。日志里另一 provider 因 `pre-consume quota failed` 失败 |
| **依赖客户端指纹** | 靠伪造 Claude Code 头才能调用。**上游随时可能改规则导致失效** |
| **成本** | 约 $0.015/次。按每日 30 条抽取 + 6 条洞察 ≈ $0.55/天，可接受但不便宜 |
| **推理模型耗时** | 单次约 13–15 秒（实测），30 条串行 ≈ 7 分钟。可接受，但不要并发太猛 |

### 建议
若用户手上有任何**官方** LLM key（DeepSeek 官方 / 智谱 / 通义 / Moonshot / Anthropic），
**优先换官方**。接口同为 OpenAI 兼容格式，改 `base_url` + `model` 即可，切换成本极低。

## 决策三：不引入数据库

### 决策
状态只存两类：
1. 本地 `data/seen_urls.jsonl` —— 已处理 URL 的 hash（幂等去重）
2. 飞书多维表本身 —— 唯一真相源

### 理由
个人自用、日增量、数据量以千计。SQLite/Postgres 属于过度设计。

### 代价
飞书 API 没有唯一约束，写入前必须**先查后写**。这是必要的复杂度，可接受。

## 决策四：调度用 Windows 任务计划程序

### 决策
不引入 Airflow / APScheduler / cron 守护进程。直接用 **Windows 任务计划程序** 每日触发一次脚本。

### 理由
- 系统原生，无额外依赖，开机自启可靠
- 需求就是"每日运行 1 次"，不需要复杂调度
- 出问题看 Windows 事件日志即可

### 备注
脚本自身需具备**幂等性**：重复运行不应产生重复数据。

## 决策五：不拆分微服务，单脚本顺序执行

### 决策
一个 Python 入口脚本，按 `fetch → clean → dedup → filter → extract → write → insight → write` 顺序执行。

### 理由
MVP 原则——最小闭环先行。每个阶段之间用本地 JSON 文件中转，
**单阶段可独立重跑**（便于 debug），但不做服务化拆分。

### 代价
全量重跑较慢。但因为是增量设计，日常运行只处理新增数据，可接受。
